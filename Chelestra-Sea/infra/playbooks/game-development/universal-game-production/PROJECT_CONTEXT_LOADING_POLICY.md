# Mandatory Project Context Loading

Revision: project-context-v1
Applies to every agent host, role and genre using this playbook.

## Correction

A cached toolchain receipt proves machine/tool availability, not that a new agent knows the project. Reading a ticket or a runbook index does not establish lore, design or production context. A short kickoff must point to the complete project reading contract rather than replace it with a remembered summary.

Before substantive work, load BOTH the universal production rules and the selected project's actual design/canon/runbook sources. This applies to artists, asset workers, engineers, researchers, orchestrators and verifiers. A code-only lane may skip execution of unused provider tools; it may not silently skip the shared project context.

## Required source layers

1. Governing repository/worktree instructions and current authorization/scope.
2. Universal playbook, its correction/supersession documents, workflow and applicable production modules.
3. Project profile/overlay, project runbooks and declared authority order.
4. Actual project design bible and lore/world/cultural/visual/mechanical constraints, not just a list of their filenames.
5. Current region/feature/character/system sources and the assigned ticket's dependencies.
6. Latest owner decisions, live issue/PR comments, implementation evidence, active work claims and source/asset status.
7. Relevant historical source material, with provenance and explicit classification; never promote an archive or proposal merely because it exists.

Each project supplies a PROJECT_CONTEXT_READSET or equivalent checked source map. It identifies common required reads, role-specific additions, source refs/locations, and how unavailable inputs are handled. A project without narrative lore must explicitly identify its equivalent product/design/visual constraints; the universal policy must not invent RPG lore for other genres.

## Resolve references before claiming readiness

Record the documentation ref separately from the implementation base and active local head. Current unmerged instructions may live on an infrastructure branch while code starts from the accepted QA base. Do not switch or merge the whole documentation branch into active code merely to read instructions.

Follow mandatory reading links to actual file contents and referenced policies/configs/templates, with a visited-source ledger to avoid duplicate reads. A folder listing, search snippet, summary, title, declared version string or another agent's READ/PASS flag is not proof of reading. Complete truncated required sections. Resolve documented archived paths from the archive's index when necessary; do not mark nonexistent top-level files read.

Review current governing sources against one another. Distinguish normative intent, owner-approved exceptions, historical proposals, and observed implementation. Existing code can prove behavior but does not by itself approve a lore/style change. Record scope-specific supersession and genuine conflicts instead of taking the most convenient source.

## Receipts and continuity

Produce a context-source ledger containing source identifier, path or URL, exact ref/commit/blob or file hash, read coverage, applicable role, authority/classification, governing decisions and unresolved conflicts. Do not put secrets in it.

A context check must include a short source-backed explanation of the project's premise, relevant geography/system, visual constraints, current-phase restrictions, implementation boundaries, quality gates and acceptance evidence. This is a comprehension summary, not a request for private reasoning.

Status:
- CONTEXT_READY: common and applicable role reads complete; required decisions resolved.
- CONTEXT_READY_LIMITED: only an explicitly separated, source-complete subtask may proceed; state the restriction.
- CONTEXT_BLOCKED: required sources missing, unread or materially conflicting.

A script can validate source identity and declared coverage, but cannot certify that an agent understands a document. Independent review still verifies that the work follows the sources.

## Cache without forgetting the project

Do not reinstall tools or repeat completed machine validation when receipts remain valid. For a genuinely new chat, load the common project context and its applicable readset. A previous agent's memory or toolchain receipt is not transferable understanding. In a continuing session with the source content retained, compare source hashes and reload changed sections plus affected dependencies. Read live scope/status/owner updates before edits and refresh live balances/approval before paid operations.

A missing source blocks only work that depends on it; do not invent its contents. Preserve ongoing work while catching up. Once the applicable context and execution gates pass, proceed with authorized work rather than generating endless planning documents.

## Reusable kickoff pattern

Start <ticket> in <project>.
Load the governing instructions, universal PROJECT_CONTEXT_LOADING_POLICY,
and the project's complete PROJECT_CONTEXT_READSET from the declared docs ref.
Read the underlying common lore/design/runbook sources and role additions,
not only indexes. Fetch live ticket/PR/owner/worktree state. Return source
coverage, comprehension, conflicts and exact isolated scope. Then continue
with authorized work when required gates pass; do not reset another worker.
